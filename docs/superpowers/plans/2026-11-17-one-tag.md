# One Tag Per Ticket From the Table (CHG-014) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The bot gives a new ticket at most one tag, chosen by the classify call from the "Gán người theo tag" table's tag names and descriptions; a ticket an HD Agent already tagged keeps only that tag.

**Architecture:** The child DocType gets a free-text `tag` and a required `description`. `routing.TagRule` carries the description; `labels.tag_choices` turns the rules into `(tag, description)` choices and `labels.chosen_tag` keeps the model's first label only when it is a choice. `prompts.build_classify_request(tag_choices=...)` replaces the module list / label catalog / alike tickets (ADR-049) with one system block. The runner drops `_label_inputs` and the old label scan.

**Tech Stack:** Frappe 15 (Python 3, tabs), Helpdesk, Frappe test runner on the shared dev site `miyano`.

**Spec:** `docs/superpowers/specs/2026-11-17-one-tag-design.md` (approved 2026-11-17).

## Review Focus

1. The model answers a tag that is not in the table (or a module name like `Stock`) → no tag is added and routing uses only agent tags / routing rules (Task 3 test).
2. The model answers two tags → at most one is added (Tasks 2 and 3 tests).
3. An HD Agent tagged the ticket before classification → the bot adds no tag and routes by the agent's tag (Task 3 test).
4. The table is empty → the classify request is byte-for-byte the request without labels (Task 3 test).
5. A tag typed with extra spaces or an accent form (`"  chấm   công "`) → stored clean, matched without case (Task 1 test).
