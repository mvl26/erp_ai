# ADR-022: Áp dụng/hoàn tác một thay đổi code = ghi file + đúng 1 commit local `--only` đường dẫn đó trên nhánh đang checkout, trong cùng job và cùng khóa chung; git ghi chỉ ở module chạy tiến trình của `changes/`, git đọc chỉ ở `source.py`; mọi lệnh git của feature tắt hook, bỏ cấu hình git chung, danh tính bot cố định; không push, không fetch, không đổi nhánh, không sửa lịch sử

- Trạng thái: proposed (FEAT-004 Amendment 1). Thay ADR-013 Quyết định 6 gạch cuối ("Không chạm `.git`, không commit, không đổi nhánh") và Quyết định 8 (tập lệnh `git` của `source.py`); sửa dòng Ràng buộc `subprocess` của ADR-013 (vẫn đúng hai file, file thứ hai chạy cả `bench` và `git` ghi). Bổ sung ADR-011 Quyết định 4 (bộ chặn đọc trạng thái git lúc đề xuất) và ADR-012 Quyết định 3 (điều kiện "hết hiệu lực"/"lỗi" mới, không thêm trạng thái). Câu "lệnh ngoài duy nhất là `git` với `log`/`show`/`diff`/`blame`" của ADR-005 Quyết định 5 được nới thêm nhóm git đọc trạng thái ở Quyết định 2 dưới đây; ADR-005 không được sửa thân

## Bối cảnh

- Mã và thiết kế hiện có (đọc 2026-11-12):
  - `source.py` chạy `git` chỉ đọc: `GIT_SUBCOMMANDS = {"log", "blame"}`, `GIT_TIMEOUT_S = 30`, `env={**os.environ, "GIT_PAGER": "cat"}` (`erp_ai/agent/tools/source.py:29`, `:55`, `:259-266`).
  - Bộ chặn đã từ chối mọi thành phần đường dẫn `.git` và tìm danh tính repo theo common git dir đi từ đích lên gốc `apps/` (`design.md:213`, `:242-244`).
  - Từ chối hoàn tác hiện đi trạng thái `Lỗi` (`design.md:632`); "file đích đã đổi" đi `Hết hiệu lực` (`design.md:415`).
- Git trên máy (Explore đọc man page đã cài, git 2.43.0):
  - `git commit -- <path>` (mặc định `--only` khi có đường dẫn) lấy nội dung working tree của đường dẫn đó, "disregarding any contents that have been staged for other paths"; đường dẫn phải đã được git biết (file mới phải `git add` trước) (git-commit(1)).
  - `git commit` chạy pre-commit, prepare-commit-msg, commit-msg, post-commit; `--no-verify` chỉ bỏ pre-commit và commit-msg. Ghi index còn gọi post-index-change; cập nhật ref gọi reference-transaction (githooks(5)). `core.hooksPath` trỏ tới thư mục khác thì git tìm hook ở đó (git-config(1)).
  - Biến `GIT_AUTHOR_*`/`GIT_COMMITTER_*` thắng `user.name`/`user.email`; `GIT_CONFIG_GLOBAL=/dev/null` bỏ `~/.gitconfig`; `GIT_CONFIG_NOSYSTEM=1` bỏ cấu hình hệ thống; `.git/config` của repo vẫn áp dụng; `--no-gpg-sign` thắng `commit.gpgSign` (git(1), git-config(1), git-commit(1)).
  - `core.fsmonitor` trong `.git/config` làm `git status` chạy lệnh ngoài (git-config(1)).
  - Commit có thể kéo theo `maintenance run --auto`/`gc --auto`; tắt bằng `maintenance.auto=false`, `gc.auto=0` (git-config(1), git-gc(1)).
  - Khóa ref thử lại tối đa `core.filesRefLockTimeout` = 100 ms (mặc định). `index.lock` đang có thì git dừng ngay, không chờ (hành vi git; man page không ghi, test AC-18 xác nhận).
  - `merge-base --is-ancestor` trả 0/1, lỗi khác 1; `rev-parse --abbrev-ref @{upstream}` trả `remote/nhánh`, không phải URL; `rev-parse --git-path` cho đường dẫn `MERGE_HEAD`, `CHERRY_PICK_HEAD`, `REVERT_HEAD`, `rebase-merge`, `rebase-apply` cả trong worktree.
- Repo app lõi trên bench (đọc 2026-11-12): không repo nào có hook cài trong `.git/hooks`; `frappe`, `helpdesk` là shallow clone, remote `upstream`; `erpnext`, `hrms` remote `origin`; `erpnext` có 10 dòng `status --porcelain`, `frappe` 1.
- `bench update` (frappe-bench 5.31.0 đã cài, Explore đọc `bench/app.py`, `bench/utils/bench.py`):
  - trước khi kéo, chạy `git status` và dừng nếu repo bất kỳ có thay đổi chưa commit hoặc file chưa theo dõi (`app.py:987-1011`); **không** kiểm commit local chưa đẩy;
  - kéo bằng `git pull <remote> <nhánh>` (merge, không rebase vì `rebase_on_pull: false`), remote = `upstream` nếu có, không thì remote đầu tiên (`app.py:1049`, `utils/app.py:215-228`);
  - `--reset`: bỏ kiểm, `git reset --hard <remote>/<nhánh>`; bench này có `shallow_clone: true` nên còn `git reflog expire --all` + `git gc --prune=all` → commit local chưa đẩy mất vĩnh viễn (`app.py:1041-1047`);
  - không đọc/đặt hook hay `user.*`.
- Điểm có thể lệch giữa các task: commit trước hay sau so byte; lúc commit lỗi thì gỡ gì; git chạy với cấu hình nào (hook, gpg, fsmonitor, cấu hình chung của máy); danh tính lấy từ đâu; lệnh git ghi nằm ở file nào; kiểm trạng thái git lúc đề xuất hay chỉ lúc áp dụng; nhánh đổi giữa duyệt và áp dụng thì sao; test chạm repo thật.

## Quyết định
1. **Thứ tự trong job áp dụng (O-1, A-16).** Toàn bộ bước dưới nằm trong khóa chung của ADR-013 Quyết định 4 và sau phép chuyển "đang áp dụng" đã commit DB (ADR-013 Quyết định 5):
   1. kiểm lại các chốt ADR-012 Quyết định 7 và dấu nội dung (ADR-013 Quyết định 6);
   2. **kiểm trước git** bằng bộ đọc git (Quyết định 3): thư mục app là repo git; HEAD nằm trên một nhánh; nhánh đó trùng nhánh đã lưu lúc đề xuất; không có merge/rebase/cherry-pick/revert dở; không có `index.lock`; file đích không bị bỏ qua và không có thay đổi staged/unstaged; ghi lại HEAD cũ, nhánh, remote/nhánh theo dõi, số commit đi trước;
   3. ghi file nguyên tử + so từng byte (ADR-013 Quyết định 6, giữ nguyên);
   4. file mới: `git add -- <đích>`; rồi `git commit --only -- <đích>` với thông điệp, danh tính và tùy chọn an toàn (Quyết định 4, 5);
   5. kiểm sau: HEAD mới khác HEAD cũ; commit có đúng 1 đường dẫn là đích; blob của đích trong commit trùng từng byte nội dung đã duyệt; HEAD cũ là tổ tiên của cha commit mới; nhánh đang checkout không đổi;
   6. phép chuyển "đã áp dụng" lưu mã commit, nhánh thật, số đi trước.
   - Sai ở bước 2 → không ghi, 0 commit: nhánh khác nhánh đã lưu → `Hết hiệu lực`; điều kiện khác → `Lỗi`, lý do cụ thể (AC-18).
   - Lệnh ở bước 4 lỗi hoặc quá giờ → **trả lại**: file về đúng byte trước (file mới thì gỡ khỏi đĩa); file mới đã `add` thì `git rm --cached -q -- <đích>`; kiểm HEAD vẫn bằng HEAD cũ và đích sạch → `Lỗi` có lý do (AC-19).
   - Bước 5 sai khi commit đã có (ví dụ người ghi đè file đích trong khoảng giữa bước 3 và 4) → `Lỗi`, lưu mã commit, **không** sửa lịch sử, lý do "commit không đúng nội dung đã duyệt, cần người kiểm".
   - Lệnh `bench` (đề xuất loại lệnh) không commit; không đổi.
   - Vì: một chỗ, một thứ tự, nên "file đổi mà không có commit" chỉ còn ở cửa sổ giữa bước 3 và 4 trong khóa, và bị trả lại. Phương án khác: commit bằng plumbing (`hash-object`/`commit-tree`/`update-ref` trên index tạm) — chính xác hơn với ref (CAS) nhưng phải tự đồng bộ index thật sau đó, không nguyên tử với `index.lock`, và cần `update-ref` (lệnh dời ref bất kỳ) trong tập cho phép; không chọn. Hoàn tác quyết định: `analyze --amend` bỏ A-4' → xóa bước 2, 4, 5 và Quyết định 2 phần ghi.
2. **Tập thao tác git (O-2, AC-23).** Hai nhóm, mỗi nhóm đúng một file:
   - **Đọc** (trong `erp_ai/agent/tools/source.py`, cạnh `log`/`blame` hiện có, không phải tool của model): `rev-parse`, `rev-list`, `status`, `check-ignore`, `ls-files`, `merge-base`, `diff-tree`, `cat-file`. Không tham số nào làm các lệnh này ghi.
   - **Ghi** (trong file chạy tiến trình duy nhất của `erp_ai/agent/changes/`, cùng file chạy `bench` của ADR-013 Quyết định 7): `add` (chỉ đích, chỉ khi file mới), `commit` (chỉ `--only -- <đích>`, có `--no-gpg-sign`; cấm `--amend`, `-a`, `--allow-empty`, `--fixup`, `--squash`, `-C`, `-c`, `--reset-author`), `rm` (chỉ `--cached -q -- <đích>`, chỉ ở nhánh trả lại).
   - Ngoài hai tập trên là cấm, gồm rõ: `push`, `fetch`, `pull`, `clone`, `checkout`, `switch`, `restore`, `branch`, `reset`, `rebase`, `merge`, `cherry-pick`, `revert`, `am`, `apply`, `stash`, `clean`, `tag`, `remote`, `config`, `update-ref`, `symbolic-ref`, `reflog`, `gc`, `maintenance`, `worktree`, `notes`, `replace`, `filter-branch`, `prune`. Không lệnh nào đọc URL remote (`remote -v`, `remote get-url`, `config remote.*`, `ls-remote`).
   - Danh sách cho phép lệnh `bench` (ADR-011 Quyết định 4) không bao giờ chứa lệnh con có chạy git trong repo app: `update`, `switch-to-branch`, `get-app`, `remove-app`, `new-app`, `setup`/`init`.
   - Vì: AC-23 cần luật grep được; `source.py` đã là chỗ duy nhất có git trong `tools/`, `changes/` đã là chỗ duy nhất có tiến trình con ghi; giữ "đúng hai file `subprocess`" của ADR-013. Phương án khác: file git thứ ba trong `changes/` (thêm một chỗ để luật phải theo); để `changes/` tự chạy cả git đọc (hai bộ đọc lệch nhau, trái Quyết định 3). Hoàn tác: thu hẹp tập lệnh trong hằng của test kiến trúc.
3. **Kiểm git cả lúc đề xuất, cùng một bộ đọc (O-3).** Bộ chặn của ADR-011 Quyết định 4, cho thay đổi code, gọi **một** hàm đọc trạng thái git trong `source.py` (nhóm đọc ở Quyết định 2) để: (a) từ chối sớm theo đúng các điều kiện của bước 2 Quyết định 1 (trừ "nhánh trùng nhánh đã lưu"), trả `ok=false` cho model, không tạo đề xuất; (b) lấy nhánh, remote/nhánh theo dõi, số commit đi trước cho đề xuất (M-4, AC-21). Job áp dụng/hoàn tác gọi lại đúng hàm đó ở bước 2. Không có đọc git nào trong request web (controller, form): form chỉ hiện giá trị đã lưu.
   - Số đi trước tính so với ref remote đã có ở máy (lần `fetch` cuối của người); feature không `fetch`.
   - Vì: AC-21 bắt comment lúc đề xuất có tên nhánh và số đi trước; người duyệt không phải duyệt một thay đổi chắc chắn sẽ lỗi; một hàm cho hai thời điểm (cùng lý do ADR-011 Quyết định 4). Phương án khác: chỉ kiểm lúc áp dụng (AC-21 không có dữ liệu lúc đề xuất); đọc trực tiếp tệp trong `.git` bằng Python (sai với packed-refs, worktree, shallow). Hoàn tác: bỏ lời gọi (a) khỏi tool đề xuất, giữ (b).
4. **Tùy chọn an toàn chung cho mọi lệnh git của feature (O-6, A-17, NFR-8).** Định nghĩa một lần trong `source.py`, `changes/` import để dùng:
   - tắt hook: `-c core.hooksPath=<thư mục rỗng do feature giữ, không nằm trong repo đích>`; `-c core.fsmonitor=false`; `-c maintenance.auto=false -c gc.auto=0`; `--no-pager`; lệnh đọc thêm `--no-optional-locks`; `commit` thêm `--no-gpg-sign`;
   - môi trường tối thiểu, liệt kê tường minh (không `os.environ`): đường dẫn tìm lệnh, `LC_ALL=C`, `GIT_CONFIG_GLOBAL=/dev/null`, `GIT_CONFIG_NOSYSTEM=1`, `GIT_TERMINAL_PROMPT=0`, cùng bốn biến danh tính (Quyết định 5) cho lệnh ghi;
   - timeout mỗi lệnh = `GIT_TIMEOUT_S` hiện có (30 s); nhóm tiến trình riêng, quá giờ diệt cả nhóm (như ADR-013 Quyết định 3). Không thêm số thời gian (NFR-3).
   - `log`/`blame` hiện có của tool đọc giữ nguyên (ADR-013 Quyết định 8 cũ), không bắt buộc đổi.
   - Vì: hook của repo có thể sửa file khác (trái NFR-7), chạy lâu, cần mạng, hoặc từ chối commit một cách không đoán được; `.git/config` và `~/.gitconfig` của máy có thể mang danh tính, ký gpg, fsmonitor. Phương án khác: chạy hook như commit của người (AC-19 vẫn bắt lỗi nhưng NFR-7 không còn kiểm được); `--no-verify` (vẫn chạy prepare-commit-msg, post-commit, post-index-change). Hoàn tác: bỏ tùy chọn `core.hooksPath` trong hằng chung; test hook đổi kỳ vọng.
5. **Danh tính và thông điệp commit (O-5, A-12, NFR-8).**
   - Tác giả = người commit = một danh tính bot cố định: tên `ERP AI Agent`, địa chỉ thuộc miền dành riêng `.invalid` (ví dụ `erp-ai-agent@bot.invalid`, designer chốt chuỗi), là hằng trong `erp_ai/constants.py`, truyền bằng `GIT_AUTHOR_NAME/EMAIL`, `GIT_COMMITTER_NAME/EMAIL`. Không lấy từ `user.*` của repo/máy, không lấy email của người duyệt hay `AGENT_USER`.
   - Thông điệp dựng **chỉ** từ trường do server giữ: thao tác (áp dụng/hoàn tác), app, đường dẫn tương đối, mã đề xuất, số phiếu, họ tên người duyệt (hoàn tác: người hoàn tác) đã lọc (một dòng; chứa `@` hoặc `://` thì thay bằng chuỗi không định danh). Không có chữ do model hay nội dung phiếu viết (lý do, diff, tiêu đề phiếu). Mẫu cụ thể do designer viết.
   - Vì: địa chỉ `.invalid` không bao giờ là của người và không định tuyến được, kể cả khi người đẩy lên GitHub; chữ của model có thể mang chuỗi bí mật (AC-13). Phương án khác: dùng `AGENT_USER` (địa chỉ thật trên miền công ty lọt vào lịch sử công khai); trường cấu hình trên ERP AI Setting (STD-DESIGN-5: spec không đòi). Hoàn tác: đổi hằng; chỉ ảnh hưởng commit sau.
6. **Nhánh (O-4, A-11).** Xác nhận: commit lên nhánh đang checkout; không tạo/đổi nhánh. Thêm: nhánh lúc áp dụng khác nhánh đã lưu lúc đề xuất (người đã đổi nhánh) → `Hết hiệu lực`, không ghi, 0 commit. Hoàn tác: commit lên nhánh đang checkout lúc hoàn tác, chỉ khi commit áp dụng là tổ tiên của HEAD (`merge-base --is-ancestor`); không thì từ chối.
   - Câu cảnh báo app lõi (AC-21) phải nói đúng hành vi bench 5.31.0 ở Bối cảnh: `bench update` không giữ commit local — nó dừng khi repo có thay đổi chưa commit, còn khi sạch thì `git pull` (merge) từ remote `upstream`/remote đầu, có thể tạo merge commit hoặc xung đột; `bench update --reset` xóa vĩnh viễn commit chưa đẩy. Người đẩy lên fork trước khi `bench update`.
   - Vì: người dặn không đổi nhánh (site chạy nhánh đó); người duyệt đã thấy tên nhánh nhận commit (AC-22), commit sang nhánh khác là trái điều đã duyệt. Phương án khác: vẫn commit lên nhánh mới và ghi lại (người duyệt không biết); nhánh phụ của bot (A-11 đã bác). Hoàn tác: bỏ điều kiện "nhánh trùng" ở bước 2; spec AC-18 bỏ trường hợp đó.
7. **Trạng thái và nhật ký (O-7).** Không thêm trạng thái (giữ máy trạng thái ADR-012 Quyết định 3):
   - commit lỗi đã trả lại → `Lỗi` (A-16); kiểm trước git sai → `Lỗi`, trừ nhánh đổi → `Hết hiệu lực`;
   - từ chối hoàn tác (file đã đổi, commit áp dụng không còn là tổ tiên của HEAD, điều kiện AC-18 sai) → `Lỗi` như từ chối hoàn tác hiện nay (`design.md:632`), 0 commit;
   - mã commit áp dụng, mã commit hoàn tác, nhánh dự kiến/nhánh thật, remote/nhánh theo dõi, số đi trước, cờ app lõi, thông điệp dự kiến là trường **trạng thái** (do module chuyển trạng thái ghi), trừ nhánh dự kiến, remote/nhánh theo dõi và số đi trước lúc đề xuất, cờ app lõi, thông điệp dự kiến: các trường này là **nội dung**, bất biến, do tool đề xuất ghi lúc tạo (ADR-012 Quyết định 1, 2). Không trường nào lưu URL;
   - dòng nhật ký áp dụng/hoàn tác thành công có mã commit (NFR-6); mỗi bước vẫn đúng một dòng.
   - Vì: trạng thái đủ để người hiểu; một trạng thái mới phải đi qua cả máy trạng thái, form, test. Phương án khác: trạng thái "đã ghi, chưa commit" (A-16 đã bác). Hoàn tác: thêm trạng thái ở ADR mới.
8. **Cô lập test (O-8, NFR-9).**
