# CHG-013 Seed Data Once at Install — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The app's data defaults (ERP AI Setting default values, and the ticket types and teams of the category mapping) are seeded once when `erp_ai` is installed; later `bench migrate` runs never seed them again. App setup that the code depends on (roles, agent account, custom fields, template rows, permissions, the panel form script) still runs on every migrate.

**Architecture:** `erp_ai/install.py`: `after_install()` = `seed_once()` + `ensure_setup()`; `after_migrate()` = `ensure_setup()` only. `seed_once()` = `_ensure_default_settings()` (without the `agent_enabled_at` mark) + `_ensure_ticket_types_and_teams()`. Existing sites get the seed exactly once through one Frappe patch `erp_ai.patches.chg013_seed_once_for_existing_sites` (runs once per site at its next migrate; on a fresh install Frappe marks every patch of the app done — `frappe/installer.py:325` `set_all_patches_as_completed` — so it never runs there). Future data defaults are added by new patches, never by `after_migrate`.

**Tech Stack:** Frappe 15 (`patches.txt` `[post_model_sync]`), Python (tabs).

**Spec:** user, 2026-11-17: "các data chung trong ERP AI Setting hay các master data cũng nên làm fix cứng như này, cài 1 lần lên site, cài 1 lần thôi, các lần migrate sau không chạy fixture này nữa"; approved split: once at install = ERP AI Setting defaults + ticket types/teams; every migrate = roles, `ai.agent` account, custom fields, template rows, Task/HD Article permissions, panel form script; future data via patches; the `agent_enabled_at` mark becomes a patch.

## Review Focus

1. A setting value a human cleared or changed after install (e.g. `category_mapping` set to `""`, `routing_rules` edited) → `after_migrate()` leaves it exactly as it is.
2. A ticket type or team a human deleted after install → `after_migrate()` does not recreate it.
3. An existing site that never got a setting default (a field added in a later version) → the one patch fills it once; a second `execute()` changes nothing.
4. A site enabled before the upgrade without `agent_enabled_at` → the patch sets the mark once, in the same `str(now_datetime())` format as today; a site with the mark keeps it.
5. `after_migrate()` still refreshes the app-owned panel form script and the custom fields (the existing tests of those steps stay green, called through `ensure_setup()`).
